# Slice generator

Three kinds of code in this app are generated, not hand-written: the domain entity (model, zod schema, service, example data), the schema-driven form component, and the manage screen (a routed CRUD list). You describe the entity once in a spec file and the `slice` schematic emits all of it in the house shape: sealed spartan primitives, signal forms with `validateStandardSchema`, a component-scoped ViewModel, icons registered with `provideIcons`, unit tests for the service and the ViewModel.

If you are about to write a `*.model.ts`, a `*.schema.ts`, a `*.service.ts`, a `*-form` component under `src/app/ui/`, or a list screen with a table, a create/edit dialog and a delete confirmation, stop and write a spec instead.

## The workflow

1. Write or extend `specs/<entity>.json` (kebab-case file name, for example `specs/book.json`). It must be valid against `schematics/slice/spec.schema.json`. The schema checks structure; the schematic also checks the cross-field rules (field references, example rows, kinds) and prints every problem it finds. Check it with `npm run validate:spec -- specs/<entity>.json`, which runs the same parser without generating anything, and fix every problem it prints before you generate or ask for the spec to be approved.
2. Run `ng generate slice --spec specs/<entity>.json`.
3. Wire the result in by hand: add a navigation link to a manage screen, show entity data on a dashboard, build any bespoke screen on top of the generated service.
4. If a generated file needs a small addition, make it in place with Edit. If it has the wrong shape, change the spec and regenerate that kind with `ng generate slice --spec specs/<entity>.json --kinds <kind> --force`. Do not rewrite a generated file, move it, rename it or write a copy beside it: the next regeneration would erase the rewrite, and a copy drifts from the one the spec describes.

When a file the run would write already exists, the schematic looks at it first. If it is identical to what the generator emits (line endings aside), it is skipped and the run prints `Unchanged: <path>`, so rerunning over your own unchanged output is safe and changes nothing. If it carries the placeholder marker `slice:placeholder`, it is replaced without `--force`: a placeholder holds nothing you need. Any other existing file stops the run: it fails with an `already exists` line for each such file and writes nothing, which protects hand-written code and your in-place edits. `--force` (the standard `ng generate` flag) replaces every such file the requested kinds produce. Use it only when every file it would replace is this generator's output or something you mean to lose, and pair it with `--kinds` so it touches only the kind whose shape you changed. Check with `git status --short <path>` for each file the run would replace: a file nobody has committed shows as untracked, and `git diff <path>` shows what forcing over a committed one would lose. If hand-written work you need is in the way, do not force: keep it and build on the generated service instead.

The schematic reads its own source from `schematics/`. That folder is read-only for you: you can read it to understand an output, but a change to what the generator emits is not yours to make. Work through the spec.

## Generating one kind at a time

`--kinds` takes a comma-separated subset of the spec's `kinds`, for example `ng generate slice --spec specs/loan.json --kinds entity` now and `--kinds form,manage` later. Without it, the run generates every kind the spec lists. A kind whose dependencies are not generated in the same run must find them on disk: `form` needs the entity's model, schema and service, and `manage` needs those plus the form component. If they are missing, the run stops, names the missing files and the command that makes them, and writes nothing. A kind the spec does not list is refused.

## Generated files

Every TypeScript file the schematic writes starts with this line:

    // @generated by the slice schematic 1.1.0 from its spec. Edit in place; reshape via the spec and --force.

The number is the generator version that wrote the file. A file with an older number was written by an older generator; regenerating it with `--kinds <kind> --force` brings it to the current output.

The generator writes, under `src/app/`, every `*.model.ts`, `*.schema.ts`, `*.service.ts`, `*.service.spec.ts` and `*-example-data.ts` of an entity, and everything under `ui/<entity>-form/`. In this app a hook enforces the part that marks a hand-built domain, but only for an entity that has a spec at `specs/<entity>.json` (for example `specs/book.json`): for that entity, a Write that creates its `*.model.ts`, `*.schema.ts` or `*-example-data.ts`, or any file under `ui/<entity>-form/`, is denied with the command that generates it. A Write over a file that carries `slice:placeholder` is denied whatever the entity. Hand-written schemas and models for features without an entity spec, such as a wizard's `<feature>.schema.ts`, are not policed. Services are not policed by the hook, because the app has services the generator does not make, such as a theme service; an entity's service still comes from the generator with the rest of the entity. Edit is allowed, so you fill and adjust generated files in place. After a shell command, the same hook reports any of those policed files that does not start with the header, because the generator did not write it.

## Order matters when entities reference each other

A `ref` field imports the target entity's service. Generate the entity that is referenced first. If `loan` references `book` and `member`, generate `book` and `member` before `loan`, or `loan` will not compile.

## What each kind emits

`entity` writes, under `src/app/<entity>/`:

- `<entity>.model.ts`: the interface and one string-union type per enum field.
- `<entity>.schema.ts`: the zod schema (one entry per field with `inForm` true, with `.meta({...} satisfies FormFieldMeta)`), exporting `<entity>Schema` and `type <Entity>FormModel = z.infer<...>`.
- `<entity>.service.ts`: a root-provided `<Entity>Service` with a private signal seeded from example data, a readonly list signal named after `plural`, `byId`, `create`, `update`, `remove`. If the entity has `ref` fields, the service also prunes references to records that no longer exist, and a many-ref field gets a `for<Target>(id)` lookup.
- `<entity>-example-data.ts`: the spec's `examples`, marked as example data. Ids are assigned `"1"`, `"2"`, and so on, by row position.
- `<entity>.service.spec.ts`: tests for seeding, create, update, remove, and reference pruning.

`form` writes `src/app/ui/<entity>-form/<entity>-form.ts`, `<entity>-form.html` and `<entity>-form.css`: a standalone `<Entity>Form` component built from the schema. It has one `hlm-field` block per form field, chosen by type, an `initialValue` input reseeded through a `linkedSignal` compared by value, a `save<Entity>` output and a `cancel` output. A `ref` field also gets a `<field>Options` input that the parent fills.

`manage` writes, under `src/app/<plural>/`, a routed screen:

- `<plural>.ts`: a thin component with `providers: [<Plural>ViewModel]`, `templateUrl` and `styleUrl`.
- `<plural>.view-model.ts`: the ViewModel with search, the select and toggle filters, the optional sort, editing state, `startCreate` (absent when the spec sets `createRoute`: create is then a link to that route), `startEdit`, `cancel`, `save`, `remove`, and the option lists for ref fields.
- `<plural>.html`: a table in a scroll container (no stacked cards), the select and toggle filters the spec asks for, an edit dialog hosting the generated form, a create dialog hosting it too (or, with `createRoute`, a create link instead), a delete confirmation dialog, an empty state, and, when the spec sets `summary`, a footer with a count, plus a "sorted by" line only when `sort` is also set. Classes are BEM on the `<plural>` block.
- `<plural>.css`: a layout-only stylesheet for those BEM classes.
- `<plural>.view-model.spec.ts`: ViewModel tests.
- It also adds a lazy route for `plural` to `src/app/app.routes.ts`, unless a route already loads `./<plural>/<plural>` under any path: then it keeps that route and its path, and adds none. If it cannot find the `routes` array literal it stops with an error instead of guessing.

## What is not generated

- Navigation. The route exists after generation; add the link to the shell yourself.
- Dashboards, stat tiles, detail pages, tabs, wizards, settings screens, and any other bespoke screen. Build those by hand on top of the generated services, with their own ViewModels.
- Cross-entity computed columns (for example a count of related records). Add a method to a hand-written ViewModel, or a bespoke screen.
- Backend access. Services are in-memory and seeded from the example data.
- More than three filters, clickable column sorting, avatar or custom cells, columns that show a `ref` field, and multi-select form controls.

## The spec

A spec is pure data. Unknown keys are rejected everywhere. Free text (labels, placeholders, help, enum options, example strings) may not contain `<`, `>`, `{`, `}`, a backtick, `$` or a backslash, and has a length cap. Identifiers are pinned by pattern: `entity` is PascalCase (`Loan`, `ReadingList`), `plural` is lowercase kebab-case (`loans`), field names are camelCase and cannot be `id` (ids are generated), icons look like `lucideTarget`.

Top level:

- `entity`, `plural`: identifiers.
- `labels`: `{ "singular": "loan", "plural": "loans" }`, the words used in screen text.
- `kinds`: any of `entity`, `form`, `manage`. `form` needs `entity`; `manage` needs both.
- `fields`: the field list, in display order.
- `examples`: optional rows of example data, one value for every field, validated against the field definitions.
- `manage`: required when `kinds` includes `manage`, forbidden otherwise.

Every field has `name`, `type`, `label`, `required`, and optionally `inForm` (default true), `placeholder`, `help`. A field with `inForm: false` is model-only: it is not in the schema or the form, and it needs a `default`, which `create` uses. Field types:

| type | extra keys | becomes |
| --- | --- | --- |
| `string` | `default` | text input |
| `text` | `default` | textarea |
| `number` | `min`, `max`, `default` | number input |
| `boolean` | `default` | switch |
| `enum` | `options` (list of strings), `default` | select |
| `date` | `default` | text input holding an ISO date string, `YYYY-MM-DD` |
| `ref` | `ref: { entity, plural, label }`, `many`, `default` | select whose options come from the target entity's service |

Rules that trip people up:

- `required` must be `true` for `number`, `boolean` and `enum`: they always have a value.
- A required single `ref` must be in the form (`inForm` true); only an optional single ref can be model-only, with `"default": null`.
- At least one field must be in the form, even for an entity-only spec.
- A `ref` points at one id (`string`, or `null` when not required). `many: true` makes it a list of ids; a many ref cannot be in the form, so it also needs `inForm: false` and `"default": []`.
- Dates are ISO strings, never `Date` objects.
- `ref.label` names the field of the target entity shown in the select. It must be a string-valued field of that entity: `string`, `text`, `enum` or `date`, never a number, boolean or ref. When the target's spec is at `specs/<entity>.json` the generator checks this (and the target's `plural`) and stops with a readable error; if that spec is not there, nothing checks it and a wrong label surfaces as a build error.

The `manage` section:

```json
"manage": {
  "icon": "lucideBookMarked",
  "createLabel": "New loan",
  "createRoute": "/loans/new",
  "columns": [
    { "field": "reference" },
    { "field": "status", "badge": { "variants": { "Returned": "default", "Overdue": "destructive" }, "fallback": "secondary" } },
    { "field": "borrowedOn" }
  ],
  "search": ["reference", "branch"],
  "filters": [
    { "field": "status", "control": "select" },
    { "field": "extended", "control": "toggle", "label": "Extended only", "icon": "lucideRefreshCw" }
  ],
  "sort": { "field": "borrowedOn", "direction": "desc" },
  "summary": true
}
```

- `columns`: the table columns in order. The first must be a `string` or `text` field and doubles as the row title. Any `enum` column can carry a `badge` mapping option values to spartan badge variants (`default`, `secondary`, `success`, `warning`, `destructive`, `outline`) with a `fallback`.
- `search`: `string` or `text` fields matched by the search box.
- `filters`: optional, one to three entries, each on a different field. `{ "field", "control": "select" }` is a dropdown on any `enum` field, listing its options plus All. `{ "field", "control": "toggle", "label", "icon" }` is a toggle button: on a `boolean` field it filters to true; on an `enum` field add `"value": "Critical"` and it filters to that option. A toggle field must be a form field, and so must the search fields.
- `sort`: optional, `{ "field", "direction": "asc" | "desc" }`, the fixed order of the rows. The field is a `string`, `text`, `number`, `date` or `enum` field. There is no clickable column sorting.
- `summary`: optional boolean. `true` adds a footer with the filtered count out of the total, plus the sort order when `sort` is set.
- `createRoute`: optional, an app path such as `/loans/new`. The create button becomes a link to that route instead of opening the create dialog, for a list whose records are created on a screen of their own. Editing and deleting stay in dialogs.
- `icon` and each toggle `icon` must be real Lucide export names from `@ng-icons/lucide`. The generator does not check that the name exists in the installed package, so confirm it if the build reports a missing export.

`schematics/slice/fixtures/` holds complete, valid specs to copy from.
